# sonaelog ― 開発の記録

## 1. このアプリは何か
家族4人（大人2人・子ども2人）の家庭用防災備蓄を、「何が・どこに・何個あり・いつ期限を迎えるか」で管理する PWA。長期保存食品・水・非常用トイレ・電池・防災用品、家族ごとの非常持ち出しリュック、日常的に消費・補充するローリングストックを一元管理する。平時はクラウドの共通在庫を家族で更新し、有事にはネットがなくても事前に同期した端末だけで在庫を検索・閲覧できる。

### 出発点となった要望（2026-11-03）
- チャットで相談して計画書（BRIEF）をまとめ、棚卸しの結果を初期データ（12の論理保管場所・129の在庫明細）として用意した。初期データは会話での棚卸しと一部写真からの判読を混ぜたスナップショットで、期限未記録や「要確認」の明細を多く含む。
- 最重要の受け入れ基準は「ネットワーク切断・再起動・セッション失効後にも、最後に同期した備蓄一覧を独立して閲覧・検索できること」。単に PWA としてインストールできることではない。
- 期限は「年月日」「年月」「未確認」が混在する。月単位の期限は月末まで有効とし、日付を捏造しない。期限の状態と、「買い替え予定」「生活用水候補」などの管理の状態は別の軸として扱う。
- 集計は確実に分かるものだけ（水は容量が分かる分だけ、食数は単位が「食」のものだけ、トイレは公称回数が分かるものだけ）。セット商品の内訳は二重に数えない。
- やらないこと：オフライン編集、通知、バーコード・OCR、購入連携、避難判断、公開共有ページ。

## 2. 主要な設計判断と、その理由
- **クラウドを唯一の正本にし、端末は完全なスナップショットを丸ごと持つ。** 差分同期やオフライン編集のマージは、家庭の低頻度な更新に対して複雑すぎる。スナップショットを1レコードとして原子的に置き換えれば、「途中まで保存された」状態が起きない。
- **閲覧の可否を認証状態から切り離す。** 災害時にトークンの更新ができないことで在庫が見られなくなるのは本末転倒。端末を操作できる人に在庫が見えるトレードオフを受け入れ、画面ロックを前提にする。
- **書き込みは RPC にまとめる。** 変更・監査イベント・revision の加算・楽観ロックを1トランザクションで保証するため。RLS を迂回しないよう `security invoker` にする。
- **初期投入は「初回だけ INSERT」。** UPSERT だと運用中の修正を上書きするため、`(household_id, seed_code)` の一意制約と `ON CONFLICT DO NOTHING` で冪等にする。
- **Supabase は無料プラン＋休止防止。** 更新頻度が低いアプリなので、1週間アクセスがないと休止する無料プランでは編集が止まりやすい。Cloudflare の無料の定期実行で3日に1回 `ping` だけを呼ぶ（費用 0 円）。
- **ログインはメールアドレス＋パスワード。** アプリ内で完結し、メール送信の制限に左右されない。家族の端末は Android のみ。
- **公開リポジトリだが、実データは入れない。** テストは架空の見本データで行い、実データでしか確かめられない受け入れ条件は gitignore された `data/checks/` に置いてローカルで実行する。
- **期限が印字されていない品は、製造年月＋「製造から○年」で期限を計算する。** ガスボンベのように製造からの年数で期限が決まる品があるため（キックオフ時のユーザーの要望）。計算結果は保存せず端末で毎回計算し、印字の期限があればそちらを優先する。年数は明細ごとに持ち、よく使う年数を候補として出す（ルール表は品名の書き方のぶれに弱い）。
- **配信は Cloudflare Workers の静的アセット＋独自ドメイン。** BRIEF は Pages を推奨していたが、独自ドメイン `sonaelog.tanijiri.dev` を CLI だけで付けられ、休止防止の cron も同じ Worker に置けるため変更した。
- **開発用の疑似クラウド（デモモード）を作る。** 開発サーバーに載せたメモリ上のバックエンドを複数のブラウザが共有するので、本番 Supabase にテストデータを入れずに「2端末の同期」や「オフライン再起動」を自動テストできる。
