- 状態：合意済み

## 👤 ユーザーが確認するところ

### 何のための機能か
作ったアプリをインターネット上に置き、家族のスマホから使えるようにします。あわせて、無料のデータベースが「使われていない」と判断されて休止しないようにします。

### できるようになること
- アプリを **`https://sonaelog.tanijiri.dev`** で公開し、家族のスマホから開ける。アドレスを知っていても、ログインしないと在庫は見えない。
  - 置き場所は Cloudflare（無料）。`tanijiri.dev` はすでに Cloudflare で管理されているので、`sonaelog` のサブドメインの設定も Claude が行う。ほかのサブドメインや `tanijiri.dev` 本体の設定には触れない。
- クラウドのデータベースは Supabase の新しい無料プロジェクト（東京リージョン）。初期データを一度だけ投入する。
- **休止防止**：Cloudflare の無料の定期実行で、3日に1回、データベースに軽くアクセスする。在庫の中身には触れない。費用 0 円。
- コードは GitHub の公開リポジトリに置く（実際の備蓄データ・設定ファイル・作業ジャーナル・計画書は含めない）。変更のたびに GitHub 上で自動テストが動く。
- 公開・更新・元に戻す手順を `docs/DEPLOY.md` にまとめる。更新（再デプロイ）は Claude が行う。

### 使い方の流れ
1. Claude がアプリを完成させ、パソコンの中の自動テストをすべて通す。
2. ユーザーに、下の「実装前に準備するもの」の作業をまとめてお願いする（ログインとパスワードの入力だけ）。
3. Claude がデータベースの作成・設定、初期データの投入、アプリの公開と独自ドメインの設定、休止防止の設定、GitHub への公開を行い、公開されたアプリで動作を確かめる。
4. 家族のスマホで実機確認をお願いする。

### かかる費用
- 0 円（Supabase 無料プラン、Cloudflare の無料枠、GitHub 公開リポジトリ。`tanijiri.dev` のドメイン代は今までどおりで、追加の費用はない）。
- Supabase の無料プランは1つの組織で同時に動かせるプロジェクトが2つまで。すでに2つ動いている場合は、作業の前にどうするか相談する。

### やらないこと
- 有料プランへの切り替え。
- `tanijiri.dev` のほかのサブドメインやメールなどの設定の変更。

### チャットで決めたこと
| 決めたこと | 理由 |
|---|---|
| Supabase は無料プランで、Cloudflare の定期実行で休止を防ぐ | 費用 0 円で、使わない週があっても編集・同期が止まらないようにするため |
| コードは GitHub の公開リポジトリ、実際の備蓄データは含めない | 記事などで公開できるようにしつつ、家の備蓄の中身は公開しないため |
| 家族の端末は Android だけを前提にする | 家族に iPhone の利用者がいないため |
| 独自ドメイン `sonaelog.tanijiri.dev` で公開する | ユーザーの要望 |

### ユーザーにお願いすること
- 実装前に準備するもの（アプリの実装とテストがすべて終わってから、まとめてお願いします）：
  - Supabase の CLI にログインする（Claude が用意するコマンドを1つ実行し、ブラウザでログイン。ログインは本人しかできないため）

  - ※ Cloudflare と GitHub は、このパソコンでログイン済みであることを Claude が確認済み
- 完成後に手で確認するもの（実機・人の判断が必要なため、Claude にはできない）：
  - 2台の Android スマホそれぞれで、`https://sonaelog.tanijiri.dev` を開いてログインし、「この端末に保存済み」と出ることを確認

  - スマホで検索・数量の変更・保管場所の確認を迷わず操作できるか（使い心地）
  - 要確認の明細を実物と見比べて直す（いつでもよい）

### 設計方針
- **配信は Cloudflare Workers の静的アセット**（BRIEF の推奨は Pages だったが変更）。`wrangler.jsonc` に `assets: {directory: "dist", not_found_handling: "single-page-application"}`、`routes: [{pattern: "sonaelog.tanijiri.dev", custom_domain: true}]`、`workers_dev: false`。`wrangler deploy` だけで独自ドメインの DNS レコードと証明書が作られる（Pages は CLI から独自ドメインを付けられず、ダッシュボード操作か API が必要）。
- 休止防止の cron も同じ Worker に載せる（`triggers.crons`、`scheduled()` で `POST {SUPABASE_URL}/rest/v1/rpc/ping`）。URL と公開キーは Worker の vars（公開キーは秘密ではない）。アセットへのリクエストは Worker のコードを通さない（`run_worker_first` は使わない）。
- `public/_headers`：CSP（`connect-src 'self' https://<project>.supabase.co`）、`X-Content-Type-Options`、`Referrer-Policy`、`sw.js` と `index.html` の `Cache-Control: no-cache`。
- Supabase：`npx supabase login`（ユーザー）→ `supabase orgs list` と `supabase projects list` で稼働中の無料プロジェクト数を確認 → `supabase projects create sonaelog --region ap-northeast-1`（DB パスワードはユーザーが入力）→ `supabase link` → `supabase db push` → `supabase config push`（`enable_signup=false`、`site_url=https://sonaelog.tanijiri.dev`）。API キーは `supabase projects api-keys` で取得し、画面に出さず `.env` に書く。
- 初期データ：`npm run seed:apply -- data/initial-data.json --household-name "わが家"`。
- アカウント：`npm run member:add -- --email <メール>` をユーザーが2回実行（パスワードは非表示入力）。
- デプロイ：`npm run deploy`（`vite build && check:bundle && wrangler deploy`）。環境変数はビルド時に `.env` から埋め込む（公開キーと URL だけ）。
- GitHub：公開前に `git ls-files` で `data/`・`.env`・`journal/`・`brief/` が含まれないことを確認 → `gh repo create sonaelog --public --source . --push`。
- `docs/DEPLOY.md`：初回構築、更新、ロールバック（`wrangler deployments list` と `wrangler rollback`。実際に確かめてから書く）、DB マイグレーションの追加手順、アカウント追加・パスワード再設定。

### 検討した案と不採用の理由
| 案 | 採用 | 理由 |
|---|---|---|
| Cloudflare Pages ＋独自ドメイン | 不採用 | 独自ドメインの追加が CLI でできず、ダッシュボード操作か API トークンが必要。Workers なら設定ファイルとデプロイだけで済み、休止防止の cron も同じ場所に置ける |
| GitHub Actions の定期実行で休止防止 | 不採用 | リポジトリに60日間更新がないと定期実行が止まる |
| GitHub 連携の自動デプロイ | 不採用 | ビルド時の環境変数を Cloudflare 側にも設定する必要があり、手元からのデプロイで足りる |
