# 005 端末内保存と同期とオフライン起動

- 状態：完了
- 依存：003, 004

## 👤 ユーザーが確認するところ

### 何のための機能か
災害でネットが使えなくても、事前に同期した端末だけで在庫を探せるようにします。このアプリで一番大事な機能です。

### できるようになること
- アプリをホーム画面に追加（インストール）できる。一度開けば、アプリの画面そのものが端末に保存され、**機内モードでもアプリを起動できる**。
- ネットにつながっているときに、家の在庫を丸ごと端末に保存する。保存は「全部そろったときだけ成功」とし、途中で失敗したら前回の保存分をそのまま使う（中途半端な状態にしない）。
- 画面の上に、いつも次の3つを表示する。
  - この端末に保存済みか（「この端末に保存済み（最終同期：2026/11/03 19:30）」または「未保存（オフラインでは使用不可）」）
  - オンライン／オフライン／同期失敗
  - 同期失敗のときは、「最終同期時点の情報です」と表示したまま、在庫は見られる（エラー画面にしない）
- 同期するタイミング：アプリを開いたとき、アプリが前面に戻ったとき、「今すぐ同期」ボタンを押したとき、オフラインからオンラインに戻ったとき。
- オフラインのときは**見るだけ**。追加・編集のボタンは押せない状態になり、「オフラインのため編集できません」と出る。保存できていないのに「保存しました」とは絶対に表示しない。
- 自分の端末で変更したら、クラウドに保存できたあと、端末の保存分も新しくする。クラウドには保存できたが端末の更新に失敗した場合は、「クラウドには保存済み・この端末は未更新」と警告して、再同期ボタンを出す。
- ほかの家族の端末は、その端末が同期するまで古いままです。そのことが分かるように最終同期日時を出す（「最新」と偽らない）。
- 端末にデータが保存されていないときは、「在庫 0 件」ではなく「この端末にはまだ在庫が保存されていません」と表示する。
- ブラウザに「この端末のデータを消さないで」とお願いする（永続保存の申請）。結果（許可／不許可）を設定画面に表示する。それでも端末の設定やブラウザのデータ消去で消えることはあるので、バックアップの書き出し（008）も用意する。
- アプリが新しい版に自動更新されても、前の版で保存した在庫は読める。読めない形式だった場合は、壊れた表示をせずに「再同期が必要」と表示する。

### 使い方の流れ
1. ネットにつながった状態でアプリを開き、ログインする → 自動で在庫が保存され「この端末に保存済み」になる。
2. ブラウザのメニューから「ホーム画面に追加」（インストール）する。
3. ふだんはアプリを開くたびに自動で最新になる。家族が変更した直後に確実に最新にしたいときは「今すぐ同期」。
4. 災害時は、機内モードやネットなしのままアプリを起動して、検索・閲覧する。

### やらないこと
- オフライン中の編集と、あとでまとめてクラウドに反映する機能。
- ほかの家族の端末への即時反映（リアルタイム更新）。開いたとき・前面に戻ったときの同期で十分とする。
- 写真の保存。

### チャットで決めたこと
| 決めたこと | 理由 |
|---|---|
| 家族の端末は Android だけを前提にする | 家族に iPhone の利用者がいないため |

### 設計方針
- PWA：`vite-plugin-pwa`（`generateSW`、`registerType: 'autoUpdate'`、`clientsClaim: true`・`skipWaiting: true` を明示。vite-plugin-pwa 2.0 では初回のページが制御下に入らず、「ログインしてすぐ機内モード」で開けなかったため）。precache は JS/CSS/HTML/アイコン/フォント（フォントはシステムフォントを使い、Web フォントは入れない）。`navigateFallback: 'index.html'`。**runtimeCaching は設定しない**（Supabase API・認証トークンを Cache Storage に入れない）。
- IndexedDB：Dexie。テーブル
  - `snapshots`：key = `${userId}:${householdId}`、値 = `{localFormat, householdId, revision, capturedAt, syncedAt, locations, lots}`。**1レコードの put で丸ごと置き換える**ので、書き込みは単一トランザクションで原子的。
  - `meta`：`lastUser {userId, householdId}`、`persist {requested, granted, at}`。
  - 書き込みは `db.transaction('rw', snapshots, meta, ...)` で snapshot と `lastUser` を一緒に更新する。
- 同期の流れ：`fetchSnapshot()` → zod で検証（002 のスキーマを共有）→ 書き込み成功後に UI の「保存済み・最終同期」を更新。失敗時は状態を `syncFailed` にし、表示は前回のスナップショット。
- 変更の流れ：`applyChange()` 成功 → `fetchSnapshot()` → 保存。2段目で失敗したら `cloudSavedLocalStale` 警告。
- 同期のきっかけ：起動、`visibilitychange`（visible）、`online` イベント、ボタン。多重実行はロックで1本に。
- オンライン判定は `navigator.onLine` と、直近の通信結果の両方で決める（`onLine` が true でも通信に失敗したら「同期失敗」）。
- `localFormat` の版を持ち、`migrateSnapshot()` で旧版→新版。未知の版は使わず「再同期が必要」。
- 「通信中に切断」の E2E は `page.route(...).abort('internetdisconnected')` で再現する（`context.setOffline(true)` は送信済みのリクエストを止めないため）。
- E2E のオフラインテストは `vite build` ＋ `vite preview`（デモモードを有効にした専用ビルド `--mode e2e`）で Service Worker を効かせる。疑似クラウドは preview サーバーにも同じプラグインで載せる。`--mode e2e` のビルドは `dist-e2e/` に出し、本番の `dist/` と分ける。

### 検討した案と不採用の理由
| 案 | 採用 | 理由 |
|---|---|---|
| ロット単位で IndexedDB に保存し差分同期 | 不採用 | 「完全なスナップショットを原子的に置き換える」ほうが壊れにくい。データ量は数百行で小さい |
| Supabase Realtime | 不採用 | 必須ではなく、他端末のオフライン保存まで即時更新されたように見える誤解を招く |
| API 応答を Service Worker でキャッシュ | 不採用 | 認証トークンや他人のデータが残る危険（BRIEF 6.2） |

### 検証方法
- 自動テスト：Vitest（fake-indexeddb で保存・失敗・移行）、Playwright（オフライン再起動、2端末、SW キャッシュの中身）。
- 実機：009 でユーザーに依頼（2台の Android でインストールと機内モード）。
