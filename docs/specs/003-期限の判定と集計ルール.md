# 003 期限の判定と集計ルール

- 状態：合意済み
- 依存：000

## 👤 ユーザーが確認するところ

### 何のための機能か
期限切れ・期限間近を正しく見分け、水や食事の量を「わかっている分だけ」正しく数えるためのルールです。間違った安心（期限が分からないのに「期限内」と出す）や、間違った合計（単位の違う数を足す）を出さないことが目的です。

### できるようになること
**期限の見分け方**（毎回、端末の中で今日の日付（日本時間）から計算する。ネットがなくても使える）
- 期限の表示は、記録されたとおり「2027年8月」または「2030年11月8日」。年月だけの期限に日にちを足さない。
- 年月だけの期限は、**その月の末日まで有効**として扱う。
- **製造年月から計算する期限**：期限が印字されていない品は、製造年月（日）に「製造から○年」を足して期限にする。
  - 例：製造 2024年5月・製造から7年 → 期限 2031年5月（5月末まで有効）。製造年月日なら日付まで計算する（2月29日に足して平年になる場合は2月28日）。
  - 表示は「2031年5月（製造2024年5月から7年で計算）」のように、計算した期限だと分かるようにする。
  - **印字された期限があれば、そちらを優先する**。製造年月は記録として残し、期限がないときだけ計算に使う。
  - 製造年月だけで年数がない、または年数だけで製造年月がないときは計算しない（期限は分からないものとして扱う）。
- 期限の状態は次の7つで、色だけでなく文字のラベルで表示する。
  - 期限切れ
  - 3か月以内
  - 1年以内
  - 期限内（1年より先）
  - 1年以内・日付未確認（「1年以内」とだけ聞いていて日付が分からないもの。「あと何日」は出さない）
  - 問題なし報告・日付未記録（棚卸しで「期限は大丈夫」と確認したが、日付は書いていないもの）
  - 期限未確認（日付も状態も分からないもの。「期限内」とは言わない）
- 期限の状態と、「買い替え予定」「生活用水候補」「優先消費待ち」などの**管理の状態は別々に**表示する。期限切れになっても、在庫から勝手に消したり、管理の状態を書き換えたりしない。

**数え方**
- 在庫の数は「明細の数」と「品物の数」を分けて表示する（129明細は129個という意味ではない）。
- **水**：容量が分かっている明細だけをリットルで合計する。合計を次の3つに分ける。
  - 飲み水として数える分（期限内・期限未確認を含む。ただし生活用水候補と期限切れは除く）
  - そのうち期限が記録されていない分（注記つきで別に表示）
  - 生活用水候補（期限切れの水、または生活用水候補にした水）
- **食事**：単位が「食」の明細だけを食数として合計する（期限内と期限切れを分ける）。それ以外の食品は無理に食数に換算せず、「食数に換算していない食品：○明細」と出す。セット商品は箱数で数え、中身（○袋）は参考として明細に表示するだけで、合計に足さない。
- **非常用トイレ**：公称の使用回数を家族が入力した明細だけを合計する。入力していない明細は「回数未入力：○明細」と出す。品名に「30回分」とあっても自動では数えない（推測を確定値にしないため）。初期データでは全明細が未入力なので、最初は 0 回＋未入力の件数が表示される。

### 使い方の流れ
1. 利用者は何もしなくてよい。ダッシュボード・一覧・明細を開くたびに、この判定で表示される。

### やらないこと
- 期限が近いことの通知（プッシュ・メール）。将来の拡張。
- 最低限そろえておく量（目標量）との比較。将来の拡張。
- 「何日分の備蓄か」の自動計算（単位が混ざっていて正しく出せないため）。

### チャットで決めたこと
| 決めたこと | 理由 |
|---|---|
| 期限が印字されていない品は「製造年月＋製造から○年」で期限を自動計算する | ガスボンベなど、製造からの年数で期限が決まっている品があるため（ユーザーの要望） |
| 印字の期限と製造年月の両方があるときは、印字の期限を優先する | 印字のほうが確実なため（ユーザー回答） |

### 設計方針
- `src/domain/expiry.ts`：純粋関数 `expiryStatus(lot, today: PlainDate)` → `{status, endDate | null, daysLeft | null}`。`today` は `Intl.DateTimeFormat('en-CA', {timeZone: 'Asia/Tokyo'})` で求める。日付は文字列と整数（年・月・日）で扱い、`Date` のタイムゾーンずれを避ける。
  - month の endDate はその月の末日。「3か月以内」：endDate ≤ today に3か月を足した日（月末は丸める）。「1年以内」：endDate ≤ today＋1年。
  - まず `effectiveExpiry(lot)` で判定に使う期限を決める：`expiry_value` があれば `{value, precision, source: 'printed'}`、なければ `manufactured_value` と `shelf_life_months` の両方があるとき `{value: 製造＋月数（精度は製造の精度のまま。日精度で存在しない日は月末に丸める）, source: 'computed'}`、どちらもなければ null。
  - 期限があれば `expiry_check` より日付を優先（`expiry_check` が古いままでも日付で判定）。
- `src/domain/labels.ts`：category・use_status・expiry_check・source・location kind・expiry_kind の日本語表示名。未知の値は値そのものを表示（勝手に「その他」にしない）。
- `src/domain/summary.ts`：`summarize(snapshot, today)` → ダッシュボード用の集計（期限別カウンタ、区分別、水、食数、トイレ、明細数／数量）。
- 区分（BRIEF 4.1）は保管場所の kind から決める：long_term＝長期備蓄、go_bag＝非常持ち出し、rolling＝ローリングストック、pending_consumption＝期限間近で取り出し済み。

### 検討した案と不採用の理由
| 案 | 採用 | 理由 |
|---|---|---|
| date-fns-tz / Temporal polyfill | 不採用 | 必要なのは日付の比較だけで、Intl と整数計算で足りる |
| 品名の「30回分」を解析してトイレ回数にする | 不採用 | 推測を確定値にしない（BRIEF 8） |
