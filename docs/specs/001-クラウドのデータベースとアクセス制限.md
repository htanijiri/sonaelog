# 001 クラウドのデータベースとアクセス制限

- 状態：完了
- 依存：000

## 👤 ユーザーが確認するところ

### 何のための機能か
家族で共有する在庫の「正本」をクラウドに置きます。家族以外の人には、見ることも書き換えることもできないようにします。

### できるようになること
- 在庫と保管場所をクラウド（Supabase の新しい無料プロジェクト）に保存する。既存アプリのデータベースとは共用しない。
- ログインした家族だけが、自分の家の在庫を読み書きできる。ログインしていない人や、別の家の人は読めないし書けない。データベース側でこの制限をかけるので、アプリの画面をいじっても突破できない。
- 同じ品名でも、期限や保管場所が違えば別々の在庫として持つ（勝手にまとめない）。
- 期限は「年月日」「年月」「なし」のどれでも記録できる。年月だけの期限に日付を勝手に足さない。
- 「賞味期限」「使用・点検期限」「期限（種類不明）」を区別して記録できる。
- **製造年月（または製造年月日）と「製造から○年が期限」の年数**も記録できる。期限が印字されていない品（カセットガスなど）は、ここから期限を自動で計算する（計算のしかたは 003）。
- 誰がいつ何を変えたかを、最低限の記録として残す（画面での詳しい履歴表示は将来）。
- 消費・廃棄で数量が 0 になった在庫は通常の一覧から消えるが、記録は残る。

### 使い方の流れ
1. 利用者がこの仕組みを直接触ることはない。アプリの画面から読み書きすると、ここに保存される。

### やらないこと
- 家族内の権限の分け方（閲覧だけの人など）。全員同じ権限。将来の拡張。
- 変更履歴を画面で詳しく見る機能。将来の拡張。
- 複数の家の切り替え（データの持ち方は将来混ざらないようにしておく）。

### チャットで決めたこと
| 決めたこと | 理由 |
|---|---|
| Supabase は新しい無料プロジェクトを作る（休止防止は 009） | 費用 0 円。既存アプリと共用しない（BRIEF） |
| 期限のほかに製造年月（日）と「製造から○年」を記録できるようにする | 使用期限が印字されていない品（ガスボンベなど）があるため（ユーザーの要望） |

### ユーザーにお願いすること
- 実装前に準備するもの：なし（クラウドへの反映は 009 でまとめて行う）
- 完成後に手で確認するもの：なし

## 🤖 実装メモ（Claude 用。ユーザーは読まなくてよい）

### 受け入れ条件
- [x] AC1：マイグレーションが PGlite 上でエラーなく適用できる（自動テスト）
- [x] AC2：未ログイン（anon）は全業務テーブルで SELECT/INSERT/UPDATE/DELETE できない（自動テスト：PGlite＋ロール切り替え）
- [x] AC3：家庭Aのメンバーは家庭Bの行を読めず、`household_id` を家庭Bに変えた INSERT/UPDATE も失敗する（自動テスト）
- [x] AC4：`get_household_snapshot()` が `{format, household_id, revision, captured_at, locations, lots}` を1回の呼び出しで返し、`archived_at` のある行を含まない（自動テスト）
- [x] AC5：`expiry_value` と `expiry_precision`、`manufactured_value` と `manufactured_precision` の不整合（`2027-13`、`2027-02-30`、precision=month なのに日付、値ありなのに precision なし）、0 以下の `shelf_life_months`、負の数量、存在しない／別家庭の保管場所参照が DB 制約で拒否される（自動テスト）
- [x] AC6：`apply_lot_change` 系の関数で更新すると `updated_at`、`households.revision` が進み、`inventory_change_events` に1行残る（自動テスト）
- [x] AC7：数量を 0 にする消費・廃棄で `archived_at` が入り、スナップショットから消え、イベントは残る（自動テスト）
- [x] AC8：（009 で確認）本番 Supabase に適用後、公開キーだけで REST から業務テーブルを読んで 0 行／権限エラーになる（コマンド：curl。009 で実施）→ 確認済み：inventory_lots・households は 42501 permission denied、get_household_snapshot も permission denied

### 設計方針
- `supabase/migrations/` に SQL を置く。テーブル：
  - `households`(id uuid, name, revision bigint default 0, created_at)
  - `household_members`(household_id, user_id → auth.users, role text default 'member', created_at, PK(household_id,user_id))
  - `storage_locations`(id uuid, household_id, seed_code null, display_name, kind check in (long_term, go_bag, rolling, pending_consumption, other), physical_note null, parent_id null, sort_order int, created_at, updated_at, archived_at null, unique(household_id, seed_code))
  - `inventory_lots`(id uuid, household_id, seed_code null, location_id, name, category, quantity numeric check >= 0, unit, expiry_value text null, expiry_precision text null check in (day, month), expiry_kind text null check in (best_before, use_or_inspection), manufactured_value text null（`YYYY-MM-DD` / `YYYY-MM`）, manufactured_precision text null check in (day, month), shelf_life_months int null check > 0（UI では年で入力。「製造から○年」）, expiry_check, use_status, source, needs_review bool, notes, liters_per_unit numeric null check > 0, kcal_per_unit null, uses_per_unit numeric null（非常用トイレの公称使用回数。初期値は null）, components jsonb null, created_at, updated_at, archived_at null, archive_reason null, unique(household_id, seed_code))
  - `inventory_change_events`(id, household_id, lot_id null, location_id null, actor_user_id, event_type, previous_value jsonb, new_value jsonb, occurred_at)
- 期限の検証は CHECK 制約＋関数 `is_valid_expiry(value, precision)`（`YYYY-MM-DD` は実在日、`YYYY-MM` は 01〜12）。DATE 型に変換して保存しない。製造年月も同じ関数で検証する。
- 製造年月から計算した期限は DB に保存しない（端末で毎回計算する。003）。`shelf_life_months` があるのに `manufactured_value` がない組み合わせは許す（あとから製造年月を入れる途中の状態）。
- 保管場所と家庭の一致は複合外部キー `(location_id, household_id) → storage_locations(id, household_id)` で強制する。
- RLS：全テーブルで有効化。ポリシーは `is_member(household_id)`（`security definer`、`auth.uid()` で `household_members` を引く）を条件にする。anon には GRANT しない。`inventory_change_events` は SELECT/INSERT のみ（UPDATE/DELETE なし）。`household_members` と `households` はメンバーの SELECT のみ（追加はサーバー側スクリプトから）。
- 書き込みは RPC（`security invoker` で RLS を効かせる）にまとめ、1トランザクションで「変更＋イベント記録＋revision 加算」を行う：`create_lot`、`update_lot`、`adjust_quantity`、`move_lot`、`consume_or_discard`、`replace_lot`（旧ロットをアーカイブ＋新ロット追加）、`split_lot`（親を減らして子ロットを作る）、`confirm_review`、`upsert_location`、`archive_location`（空のときだけ）。revision 加算はトリガーで行う。
- 楽観ロック：更新系 RPC は `expected_updated_at` を受け取り、違えばエラー（他の家族の同時編集を上書きしない）。
- 読み取りは `get_household_snapshot()`（`stable`、1 文の SELECT で JSON を組み立てるので一貫したスナップショットになる）。ユーザーが複数家庭に属する将来に備え、引数 `p_household_id` を取り、省略時は唯一の所属家庭。
- `ping()`：anon に EXECUTE を許可し、`true` だけを返す（009 の休止防止用。業務データに触れない）。
- テスト：PGlite に `auth` スキーマのスタブ（`auth.users`、`auth.uid()` は `request.jwt.claims` を読む）と `anon`／`authenticated` ロールを作り、同じマイグレーションを流す。

### 検討した案と不採用の理由
| 案 | 採用 | 理由 |
|---|---|---|
| テーブルへ直接 INSERT/UPDATE | 不採用 | 監査イベントとの一貫性、楽観ロックを1か所で保証したい |
| security definer の RPC | 不採用 | RLS を迂回するため、所属確認の書き漏れが致命的になる |
| 数量 0 の行を物理削除 | 不採用 | 履歴を残す（BRIEF 9.1） |
| RLS テストを本番 Supabase で行う | 不採用 | 本番にテストデータを入れない（BRIEF 7） |
