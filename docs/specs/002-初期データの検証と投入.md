# 002 初期データの検証と投入

- 状態：合意済み
- 依存：001

## 👤 ユーザーが確認するところ

### 何のための機能か
棚卸しでまとめた初期データ（12か所・129明細）を、クラウドに一度だけ、間違いなく入れるための仕組みです。

### できるようになること
- 投入の前に、初期データにおかしなところ（ありえない日付、マイナスの数量、存在しない保管場所、件数の食い違いなど）がないかを検査し、あればどの明細のどこがおかしいかを表示して止まる。
- 初期データをクラウドに入れる。**2回実行しても二重に登録されず、アプリで直した内容も上書きしない。**
- 初期データの中身は、そのまま入れる。期限が書かれていないものに日付を足したり、写真から読み取った仮の明細を推測で直したりしない。写真由来の明細は「要確認」のまま入る。
- 初期データに含まれない品（たとえば「備蓄ではない」と訂正された品、購入予定の品）は登録されない。

### 使い方の流れ
1. Claude が検査を実行し、問題がないことを確かめる。
2. Claude が投入を実行する（009 でクラウドを用意したあと）。

### やらないこと
- 初期データの不明点（期限、写真由来の品名・数量、保管場所の階や棚）を推測で埋めること。アプリの「要確認」画面で家族が直す（007）。
- バックアップからの復元（取り込み）。BRIEF でも必須ではない。

### チャットで決めたこと
| 決めたこと | 理由 |
|---|---|
| 初期データは Git に含めず、このパソコンの `data/` からだけ投入する | 公開リポジトリに家の備蓄の中身を入れないため |

### ユーザーにお願いすること
- 実装前に準備するもの：なし
- 完成後に手で確認するもの：なし

### 設計方針
- 検証は `src/domain/seedSchema.ts`（zod）に書き、CLI とアプリ側のスナップショット検証（005）で共有する。
- CLI：`scripts/seed.ts`（tsx で実行）。
  - `seed:validate <file>`：検証のみ。ネットワークに出ない。
  - `seed:apply <file> --household-name <名前>`：`.env` の `VITE_SUPABASE_URL` と `SUPABASE_SECRET_KEY` を使い、RPC `seed_household(payload jsonb)` を呼ぶ。
- `seed_household` は service_role だけが実行できる関数。1トランザクションで、家庭がなければ作り（`households.seed_key` で一意）、保管場所→明細の順に `INSERT ... ON CONFLICT (household_id, seed_code) DO NOTHING`。既存行は一切更新しない。挿入件数／スキップ件数を返す。
- 投入時のイベントは `event_type='seed'` で記録する。
- 初期データにない列（`expiry_kind`、`manufactured_value`、`shelf_life_months`、`uses_per_unit`）は null で入れる。スキーマ上は省略可能な項目として受け付ける（`schema_version` は 1 のまま）。
- 写真由来の注意（モバイルバッテリーの除外など）は初期データに反映済み。スクリプト側で品名による特別扱いはしない。
- `metadata` のうち `home_equipment` などは DB に入れない（在庫ではないため）。ダッシュボードの補足表示はしない（BRIEF でも「在庫の補足情報」扱いで、画面要件にない）。

### 検討した案と不採用の理由
| 案 | 採用 | 理由 |
|---|---|---|
| UPSERT | 不採用 | 運用中の修正を上書きする（BRIEF 5.2） |
| supabase-js でテーブルごとに INSERT | 不採用 | 途中失敗で中途半端な状態が残る |

- 実データ：`data/checks/` のテストで 12／129 を確認（ローカル限定）。
