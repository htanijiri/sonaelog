# 010 食料品の味の感想

- 状態：完了
- 依存：007, 009

## 👤 ユーザーが確認するところ

### 何のための機能か
非常食は、ローリングストックで食べてみるまで味が分かりません。食べたときの感想を残しておけば、次に買い替えるときに「また買う／もう買わない」を家族で判断できます。

### できるようになること
- 食料品に、**品名ごと**の味の感想を残せる。内容は2つ。
  - 3段階の評価：「また買う」「ふつう」「もう買わない」（付けなくてもよい）
  - 短いコメント（500文字まで。付けなくてもよい）
- 感想は**家族で1つを共有**する。ログインした大人なら誰でも書き直せる。子どもの感想は大人が代わりに書く。最後に直した日時が表示される。
- 同じ品名の明細（期限や保管場所が違うもの）には、すべて同じ感想が表示される。
  - 品名の全角・半角の違いと、前後や連続する空白は、同じ品名とみなす。
  - 品名を変えると、別の品として扱う。感想は元の品名のほうに残る。
- 食べ切って在庫がなくなっても、感想は残る。新しい画面「**味の感想**」で、在庫がなくなった品も含めて感想の一覧を見られる。今の在庫数（なくなった品は「在庫なし」）も表示する。
- 在庫一覧では、食料品の行に評価が小さく表示される。キーワード検索では、感想のコメントも検索の対象になる。
- 食料品を追加するとき、同じ品名の感想がすでにあれば、入力画面にその感想を表示する（買い直す前の参考に）。
- ネットがつながっていないときも、最後に同期した感想を見られる。**書けるのはオンラインのときだけ**（在庫の編集と同じ）。
- 書き出し（JSON・CSV）に感想も含める。

### 使い方の流れ
1. 食料品を食べたら、在庫一覧などからその品の明細を開く。
2. 「味の感想」の欄で「感想を書く」を押し、評価とコメントを入れて保存する。
3. 次に買い物をするときは「味の感想」の画面か、同じ品の明細で感想を見る。
4. 感想を消したいときは、同じ画面で「感想を消す」を押す。

### かかる費用・データの送り先
- 費用は増えない。感想は在庫と同じ Supabase のデータベースに保存し、ほかのサービスには送らない。

### やらないこと
- 食料品以外（水・電池など）の感想。
- 家族一人ひとりの別々の感想や、感想の履歴（食べるたびに追加していく形）。
- 写真の添付、星の数による細かい評価。
- 評価での絞り込み・並べ替え（必要になったら追加する）。

### チャットで決めたこと
| 決めたこと | 理由 |
|---|---|
| 感想は明細ごとではなく品名ごとに付ける | 食べ切って明細がなくなっても感想が残り、次に買うときの参考になるため（ユーザー回答） |
| 3段階の評価（また買う／ふつう／もう買わない）と自由記述のコメント | 一覧でひと目で分かり、買い替えの判断に使いやすいため（ユーザー回答） |
| 家族で1つの感想を共有し、大人が書き直す | いちばん単純で、子どもの感想も大人が代わりに書けば足りるため（ユーザー回答） |
| 対象は食料品だけ | ご要望の範囲（ユーザー回答） |

### 設計方針
- **DB**：新しいマイグレーションで `public.food_reviews` を作る。
  - 列：`id uuid pk`、`household_id uuid`（households へ FK）、`name_key text`、`display_name text`、`rating text null check (rating in ('again','ok','never'))`、`comment text not null default '' check (char_length(comment) <= 500)`、`created_at`、`updated_at`、`updated_by uuid`（auth.users）。
  - `unique (household_id, name_key)`、`check (rating is not null or comment <> '')`。
  - RLS は既存の業務テーブルと同じ形（`private.is_member(household_id)`）。anon への権限なし。
  - 正規化キーは `private.food_name_key(text)`（`normalize(…, NFKC)`、trim、`\s+` → 半角空白1つ）。`private` スキーマに置く。
- **RPC**：`get_household_snapshot` を `create or replace` して `food_reviews` 配列（household_id を除く）を追加する。スナップショットの `version` は 1 のまま（項目の追加だけで、古いクライアントは知らない項目を無視する）。`apply_change` を `create or replace` して `set_food_review` を追加する。
  - 入力：`{type:'set_food_review', name, rating, comment, expected_updated_at}`。`expected_updated_at` が null なら「まだない」前提で、既にあれば SL409。
  - 書ける条件：同じキーの有効な food の明細があるか、既存の感想がある（SL400）。
  - 評価もコメントも空なら削除する。監査イベントは既存の `inventory_change_events` に `lot_id = null`、種類 `food_review_create`／`food_review_update`／`food_review_delete` で記録する（`lot_id` はもともと null 可）。
  - 既存の `apply_change` は `private._apply_change_core` に移し（`alter function … set schema private` と rename）、新しい `public.apply_change` が `set_food_review` だけを処理して、それ以外は委ねる。既存の処理を書き写さずに済み、差分が小さい。
  - 削除にも revision を加算するため、`TG_OP` で OLD/NEW を切り替えるトリガー関数 `private.bump_household_revision_any()` を足す。
- **ドメイン**：`types.ts` に `FoodReview`、`Snapshot.food_reviews`（スキーマでは省略可、既定は []）。`foodNameKey()` を `src/domain/foodReviews.ts` に置く。`changes.ts` に `set_food_review` を追加（疑似クラウドもこれを使う）。`search.ts` は食料品の明細に感想のコメントと評価の表示名を検索対象として足す。`exportData.ts` に追加。
- **画面**：
  - 明細の画面（食料品のみ）に「味の感想」の欄。編集のダイアログは、評価（また買う／ふつう／もう買わない／付けない）とコメント。編集の可否は既存の判定（オンライン・ログイン済み・同期中でない）を使う。
  - 一覧の行に評価の小さなバッジ。
  - 新しい画面 `/food-reviews`「味の感想」：評価の順（また買う→ふつう→もう買わない→評価なし）、その中は品名順。今の在庫数（同じキーの有効な明細の合計。単位が混ざる場合は単位ごとに表示）。在庫一覧の検索欄の下から開けるリンクを置く。明細が複数ある品は「明細を見る」で在庫一覧（品名で検索・食品で絞り込み）に移る。
  - 追加画面で、カテゴリが食料品かつ品名が既存の感想と一致したら、その感想を表示する。
- **見本データ**：疑似クラウドは `fixtures/sample-food-reviews.json`（架空）を読み込んで感想を数件入れる（初期データのファイル形式は変えない）。
- **本番**：`npx supabase db push --remote` → `db advisors` → `npm run deploy`。DB を先に更新する（古いアプリは新しい項目を無視するので、順番の入れ替わりで壊れない）。

### 検討した案と不採用の理由
| 案 | 採用 | 理由 |
|---|---|---|
| 明細の `notes` に感想を書く | 不採用 | 明細ごとになり、食べ切ると見えなくなる（ユーザー回答と矛盾） |
| 明細に感想の列を足し、買い替え時に引き継ぐ | 不採用 | 同じ品名の明細が複数あると食い違う。分割・移動のたびに引き継ぎが要る |
| スナップショットの version を 2 に上げる | 不採用 | 項目の追加だけで、古いアプリでも読める形のままにしたほうが、更新の順番に左右されない |
